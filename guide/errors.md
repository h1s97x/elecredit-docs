# 错误码

Elecredit 的错误分为四类：**认证域**、**业务**、**限流**、**参数/上游**。
分类决定「该改什么」，比错误码本身更重要。

## 认证域（不要重试）

| code | 含义 | 处理 |
|---|---|---|
| `SYS001` | 签名校验失败 | 检查 `appKey`、签名算法、body 是否紧凑 JSON 且中文不转义 |
| `SYS002` | 请求过期 | 时间戳必须是**毫秒**；同步本机时钟（NTP） |
| `SYS003` | 应用 ID 不存在 | 核对 `app-id` 是否与后台一致 |
| `SYS004` | 签名算法不支持 | Header 固定 `sign-type: MD5` |
| `SYS006` | IP 受限 | 联系服务商把出口 IP 加入白名单 |

::: warning 认证域错误不要重试
重试只会消耗时间，不会改变结果。逐个核对上面「处理」列的项。
最常见的根因是 **body 序列化不一致**（见[签名算法](./signature)）。
:::

## 业务响应（不是错误）

| code | 含义 | 处理 |
|---|---|---|
| **`SYS005`** | **余额不足** | **提示充值，不重试** —— 签名已通过 |
| `000` | 查询成功 | 正常取数 |
| `001` | 查询成功但无结果 | 正常业务响应，不是错误 |

:::: danger 把 SYS005 当成认证失败是最常见的无效排错
它意味着**签名算法正确、凭据有效、API 可达**，只是账户余额不足。
去改签名、换 App Key、怀疑序列化——全都是白费功夫。
::::

## 限流（降速后重试）

| code | 含义 | 处理 |
|---|---|---|
| `SYS008` | 频率限制 | 降低请求频率，指数退避重试 |

两个客户端的退避策略（已内置）：

| 客户端 | 退避 | 最大次数 |
|---|---|---|
| Node CLI | `min(1000 · 2ⁿ, 8000)` ms + 20% 抖动 | 3 |
| Python SDK | `2ⁿ × 0.1` s | 3 |

::: tip 扇出调用要特别小心计费
`D11` 多类型扇出、`F09` 深层穿透会成倍放大调用次数——每次分页都是一次**计费调用**。
并发调高时既容易触发 `SYS008`，也会推高计费峰值。
:::

## 参数错误

| 现象 | 含义 | 处理 |
|---|---|---|
| HTTP `400` | 请求体校验失败 | 修正字段名与取值 |
| `400 企业信息不能为空` | 参数名写错 | `B04` 与 `P0020019` 必须用 `entInfo`，不是 `entName` |
| `400 type值不在允许范围内` | `D11` 的 `type` 非法 | 用 [D11 的 12 个合法 type 值](../api/judicial)之一，**大小写敏感** |
| `999 系统异常` | `D11` 的 `range` > 20 或 `pageNo` 超总页数 | `range` 上限 20 |
| `SYS044 资源不存在` | 路径大小写错误 | `P0020019` 必须是小写 w 的 `/saic/SaicinvWh` |

## 服务与网络

| 现象 | 含义 | 处理 |
|---|---|---|
| HTTP `5xx` | 上游异常 | 有界退避重试 |
| 网络错误 / 超时 | 网关或链路问题 | 重试 1 次，仍失败则报告 |
| `F09` 长时间无响应 | 深层穿透数据量大 | 该端点**超时是 60s**，不要过早判定失败 |

## 常见「看起来是错误」的正常情况

| 你看到的 | 实际情况 |
|---|---|
| `code: "SYS005"` | 签名正确，账户没余额 → 充值即可 |
| `code: "001"` | 查询成功，只是没有匹配数据 |
| `SYS044 资源不存在` | 很可能是**路径大小写**写错了（同码复用了「路径不存在」） |
| `resultData.xxxCount: ""` 或键缺失 | 该类型无数据，属正常，归一为 0 处理 |
| 传了 `types` / `startDate` 没报错但没效果 | 上游**静默忽略**这些字段，见 [D11](../api/judicial) |
